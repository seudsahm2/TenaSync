# Doctor Module - Detailed Implementation Plan

## 1. Overview
Upon reviewing the existing codebase in `src/modules/doctor/`, it is clear that the **backend API logic is nearly 80% complete**. Features for Profile Management, Patient Management, Consultation Handling, and Document Management have all been successfully implemented in `routes.ts` and `service.ts`. 

However, the module currently lacks a **Frontend User Interface** and the backend **Availability/Scheduling system**. This plan outlines exactly how to complete these missing pieces to make the Doctor Module fully functional and integratable.

## 2. Outstanding Gaps to Address
1. **Frontend Application**: `src/public/modules/doctor/` contains only an empty `app.js`. Doctors need a clean dashboard to interact with patients, read AI summaries, and manage their profiles.
2. **Availability Management**: Mentioned in Phase 3 of the original plan, doctors need a way to declare when they are available for telehealth or in-home visits.
3. **Module Exports**: Missing an `index.ts` export hub to easily expose the `doctorService` to other modules.

## 3. Step-by-Step Execution Plan

### Phase 1: Frontend Architecture & Foundation
- [ ] **Create Directory Structure**: Set up `views/` and `css/` inside `src/public/modules/doctor/`.
- [ ] **Main Layout (`dashboard.html`)**: Create the core layout featuring a responsive sidebar navigation with tabs for: "Dashboard", "Patients", "Consultations", and "Documents".
- [ ] **Styling (`style.css`)**: Implement professional, clean, medical-themed CSS (e.g., using TenaSync green/blue branding).
- [ ] **State Management (`app.js`)**: Implement a simple Vanilla JS router to switch between the tabs without reloading the page, and handle authentication headers (e.g., injecting `x-doctor-id` for testing).

### Phase 2: Building the Views
- [ ] **Profile & Dashboard View**: 
  - Call `GET /api/doctor/profile/:id/stats` to render KPI cards (Total Patients, Active Consultations).
  - Create a form that loads data from `GET /api/doctor/profile/:id` and updates via `PUT`.
- [ ] **Consultation Workspace**: 
  - Call `GET /api/doctor/consultations` to display an inbox of active chats.
  - Implement the Chat UI. When opening a chat, display the `aiSummary` (generated by the AI Assistant) clearly at the top.
  - Add a "Manual Takeover" button (`POST /takeover`).
  - Add an input box to reply directly to patients (`POST /message`).
- [ ] **Patient List View**: 
  - Call `GET /api/doctor/patients` and render a table of assigned patients.
  - Clicking a patient fetches their history.
- [ ] **Document Manager**: 
  - Create a file upload UI to `POST /api/doctor/documents`.
  - Display existing documents in a list with a "Delete" button.

### Phase 3: Backend Availability System
- [ ] **Schema Update**: Add a `DoctorAvailability` model to `prisma/schema.prisma` mapping to `clinicianId`.
- [ ] **Service & Routes**: 
  - Add `setAvailability`, `getAvailability`, and `deleteAvailability` in `service.ts`.
  - Add matching `POST`, `GET`, `DELETE` endpoints in `routes.ts`.
- [ ] **Frontend**: Add an "Availability" tab to the dashboard to let doctors select time slots.

### Phase 4: Integration & Polish
- [ ] **Export Hub**: Create `src/modules/doctor/index.ts` to export `doctorService`, `routes`, and types so the Patient module can easily fetch doctor availability natively.
- [ ] **Root Integration**: Provide a `window.DoctorDashboardWidget` (similar to the AI Assistant) or a clear entry point so the main app can mount the doctor UI upon successful login.

By following this plan, the Doctor Module will quickly transition from a headless API to a full-fledged product that smoothly integrates with the Patient and AI components.
